The 5 SOLID Principles at a Glance

These five foundational principles guide developers in creating understandable, flexible, and maintainable object-oriented designs.

🎯

Single Responsibility

A class should have only one reason to change, meaning it has a single, well-defined job.

📖

Open/Closed

Software entities should be open for extension, but closed for modification.

🔄

Liskov Substitution

Objects of a superclass should be replaceable with objects of its subclasses without errors.

🧩

Interface Segregation

Clients should not be forced to depend on interfaces they do not use.

🔌

Dependency Inversion

High-level modules should depend on abstractions, not on concrete low-level modules.

The Dependency Rule

The core principle is that source code dependencies can only point inwards. Nothing in an inner circle can know anything at all about something in an outer circle. This protects the core business logic from changes in volatile outer layers.

A MERN Project Blueprint

Here’s how these concepts translate into a tangible folder structure for a Node.js/Express.js backend, promoting separation of concerns.

📁

src/presentation/

Entry point. Handles HTTP requests, routing (Express.js), and middleware. The bridge to the outside world.

↓
⚙️

src/application/

Contains application-specific business rules. Orchestrates use cases and calls on domain abstractions.

↓
🏛️

src/domain/

Core business logic. Contains entities and abstract interfaces for repositories and services.

↓
💾

src/infrastructure/

Concrete implementations. Connects to databases (MongoDB), external APIs, and other low-level details.
